Why we moved our build system

For years, our build system grew the way most build systems grow: one script at a time. Someone needed to generate code from a schema, so a script appeared. Someone else needed to bundle assets, so another script appeared, calling the first one. By the time we noticed, a clean build took nearly forty minutes, incremental builds were unreliable, and nobody felt confident changing anything in the build directory. New engineers would spend their first week learning which commands to run in which order, and which errors could be safely ignored.

We considered a few options. The first was to keep the existing scripts and add caching on top. This would have been the cheapest change, but caching a system whose inputs and outputs are not declared tends to produce subtle bugs: stale outputs that look correct until they don't. The second option was to adopt a general-purpose build tool with strong support for declared inputs and outputs. That promised correctness and good caching, but it meant rewriting a lot of build logic and teaching the whole team a new tool. The third option was a middle path: keep our language-specific tools, but put a thin orchestration layer on top that requires every step to declare what it reads and writes.

We chose the third option. The orchestration layer is small, around a thousand lines, and most of it is about hashing inputs and checking whether outputs are up to date. Each build step is still the familiar compiler or bundler command, so engineers didn't have to learn a new language. What changed is that every step now lists its inputs explicitly, and if a step reads a file it didn't declare, the build fails in continuous integration. That one rule caught dozens of hidden dependencies in the first month.

The results have been encouraging. Clean builds now take about eleven minutes on a developer laptop and six minutes in CI, where the remote cache is warm. Incremental builds after a typical change take under a minute. More importantly, people trust the build again: when it says something is up to date, it is. We've also been able to delete a surprising amount of code, because several scripts existed only to work around ordering problems that the new layer handles automatically.

There were costs. The migration took one engineer most of a quarter, with help from others during the final weeks. Some steps were hard to express with explicit inputs, especially code generators that scan whole directories, and we had to restructure a few of them. We also had to invest in good error messages, because a build that fails with a cryptic hash mismatch is not much better than one that silently produces stale output.

If you are considering a similar move, our advice is to start by measuring. Find out where the time actually goes, and which steps are flaky. Then pick the smallest change that makes dependencies explicit. You can always adopt a bigger tool later, and the work of declaring inputs and outputs will carry over.
